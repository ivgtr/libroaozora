2026-09-06 JST。ユーザーが合意した「公式取得・本文はアクセス時のみ保存」を前提とする。
更新: 以下の7項目の推奨方針にもユーザー合意を得て、[実装計画](./official-origin-plan.md)へ反映した。未実装。

## 1. ブラウザまでの更新反映

### 判断

更新を扱う最終段階ではブラウザまで対象にする。ただし、公式への切り替えのリリース条件にはしない。
「読むたび即座に最新版」と「オフラインでも保存済み本文を読む」は両立しないため、
オンラインで一定期間ごとに再確認する方式を採用する。

### 推奨仕様

- IndexedDBの `lastAccessedAt` は削除判断用として残し、別に `checkedAt` を持つ。
- オンラインで作品を開くとき、最終確認から24時間以上なら再検証する（初期提案値）。
  全作品を巡回するタイマーは作らない。
- 通信失敗は確認成功と扱わず、`checkedAt` を更新しない。
  明示的な利用停止・作品不存在と、一時的な取得障害は区別する。
- API応答に実際に返した本文の識別子と検証状態を追加し、中継もブラウザへ伝える。
  新フィールドは互換性を保つ追加とし、旧応答・旧IndexedDBエントリは未検証として扱う。
- CDNからの応答や上流の旧版フォールバックを、公式の最新版を確認できた結果とは扱わない。
  アプリがAPIへアクセスした時刻と、サーバーが確認したメタデータ世代・状態は分ける。
- 初期のCDN方針は正常応答の1時間キャッシュを維持し、更新保証を導入する段階で
  現行24時間のstale-while-revalidateは外すか短縮する。旧版フォールバック応答は長期共有キャッシュしない。
- 読書開始前の再検証で新版を取得できれば新版を使う。表示済み本文はその読書中に差し替えない。
  オフライン等で旧版を開いた後の更新は、次に開くときに反映する。

読書位置は本文識別子とセットで保存する。新版へ切り替わって識別子が違う場合、古い文番号をそのまま適用しない。
初期実装は短い通知とともにその作品の再開位置を先頭に戻す案が簡単で確実。
お気に入り・読了履歴・累積記録は維持する。文脈からの位置復元は別機能とする。

日次メタデータ同期、サーバーの短い参照キャッシュ、CDN、ブラウザの再検証間隔が重なる。
障害なしで継続利用する場合は概ね2日＋CDN等の遅延を目安にできるが、厳密な反映期限ではない。
開かない作品・オフライン端末・表示し続けた画面には更新を強制しない。

### 検証

頻繁に読んでも再検証時刻が延びないこと、再検証失敗で時刻が更新されないこと、
旧版フォールバックを最新版と誤認しないこと、読書中の本文と位置が変わらないことを確認する。

## 2. 公式停止時の旧版提供

### 判断

一時障害時は保存済みの正常な本文を優先する。ただし、提供停止を示す情報は優先する。
削除や著作権変更を検知したのに「キャッシュがあるから返す」という経路は作らない。

| 状況 | 推奨動作 |
| --- | --- |
| 同じ更新版の正常キャッシュあり | 公式へ行かず返す |
| 新版取得で通信失敗・タイムアウト・429・5xx | 現在のメタデータが提供を許す作品に限り、正常な旧版があれば返す |
| 同条件で旧版なし | 再試行可能な取得エラー |
| 公式403・404・410 | 初期実装では旧版にフォールバックしない。保存データ自体は削除しない |
| メタデータで作品削除・著作権制限・本文URL削除を検知 | 通常の存在・権利チェックで提供を止める |
| 新しいZIPが不正 | 不正データを保存せず、初期実装では取得エラー。原因を確認する |
| R2読出しの一時失敗 | オブジェクトを削除せず、公式取得へ進む |

正常な旧版とは、実際に展開・デコード・基本的な本文検証を通った保存データ。
移行前のZIPも読めれば旧版候補にできるが、最新版確認済みと後付け認定しない。
旧版は旧版の識別子で返す。新版のキーへコピーしない。

旧版提供のログと、最終同期成功からの経過時間を残す。
同期失敗が継続した場合は知らせるが、単に一定時間経ったという理由で正常本文を自動停止させない案を推奨する。
未検知の取り下げを即時に反映できないこと、既にオフライン保存された本文を遠隔で回収できないことは仕様の限界。

## 3. 更新版の識別と競合

### 判断

作品IDだけの上書きキーをやめ、メタデータから得た版をキーに含める。
分散ロックを導入する前に、別版同士が上書きし合わない構造にする。

### 推奨仕様

- `sourceRevision = hash(完全な本文URL, 本文更新日, 修正回数, 識別方式のバージョン)`。
- KV: `content:v2:{workId}:{sourceRevision}`。
- R2: `content/v2/{workId}/{sourceRevision}.zip`。
- R2には取得元、取得日時、更新識別子、取得したZIPのハッシュを添える。
  本文の識別にはデコード後本文のハッシュも利用できる。
- 不完全な更新情報は明示的に欠損として正規化する。空欄を現在日時で埋めない。
- 本文ハッシュと構造化処理の形式バージョンを分ける。パーサー変更でもブラウザの文番号は変わり得る。
- 旧版フォールバック候補は、直前の保存メタデータ世代が示す版と移行前キーなど、少数の既知候補に限定する。
  見つからなければ旧版なしとする。本文APIでバケット全体を走査しない。
- 完了順で自由に更新される共有の「最新本文」ポインターは初期実装では設けない。

これで旧メタデータのリクエストが遅く完了しても、新版キーを上書きしない。
ただし、公式CSVとZIPは一つのトランザクションで公開されるとは確認していない。
`sourceRevision` は取得時に参照した配布情報であり、その版とファイルの完全一致を公式が保証したものではない。
同じ識別子で異なる本文ハッシュを観測した場合は異常として記録し、再検証対象とする。
R2の同一キーへの競合書込みは条件付き保存等で既存正常データを保護する実装を確認する。

旧版整理は現状のデータ量を測定して別途実施する。現行版を時間だけで削除するlifecycleは設定しない。

## 4. メタデータの公開単位

### 判断

作品・著者・同期日時を一つのスナップショットにする。
大量のキーを一斉に整合させる方式は現時点では不要。

2026-09-06取得の公式CSVを既存coreパーサーで変換した測定値:

- 作品17,840件、人物1,335件。
- `{works, persons, syncedAt}` のJSONは11,309,473 bytes（約10.79MiB）。
- 本文更新情報を追加する前の値。実装後に再測定する。

KVの値上限は25MiBなので現状は一つの値に収まる。ただしシリアライズサイズが収まることと、
実行時のメモリ・CPUが十分なことは別に検証する。[KV limits](https://developers.cloudflare.com/kv/platform/limits/)

### 推奨する保存・公開

1. 同期ジョブで全CSVを取得・解析・検証し、世代ID付きの単一JSONを作る。
2. `metadata/snapshots/{generation}.json` をR2へ保存する。
3. 保存完了を確認してから、小さなR2の `metadata/current.json` を切り替える。
   currentには現世代と直前世代を記録する。
4. KVは `metadata:{generation}` の単一JSONをキャッシュする。KV保存失敗でもR2から復元できる。
5. APIはcurrentを確認し、その世代のKV、なければ同世代のR2を読む。
   currentの実行環境内キャッシュは初期提案60秒。公式へのアクセスは伴わない。
6. 現世代が取得できないとき、明示的に旧世代へフォールバックしてログを残す。
   作品だけ新、著者だけ旧という組合せは返さない。

KVには反映遅延があり、キー不存在の結果もキャッシュされるため、参照先の公開判定をKVだけに任せない。
R2の直接読書きは強い整合性を持つが、複数オブジェクトを一括更新するトランザクションではない。
そのため本文を先に保存し参照先を最後に切り替える順序が必要。
[KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/)、
[R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)

currentの更新者は同期ジョブに限定し、workflowのconcurrencyで直列化する。
古いジョブが遅れて公開されることを防ぐ。手元から同期する場合も同じ運用経路に寄せる。
旧世代はロールバック・旧本文候補の特定に使い、少なくとも直前の正常世代を残す。

注意点: dayroaozoraはメタデータと本文を並列リクエストするため、リクエストをまたぐ世代一致は自動的には保証されない。
まず各応答にメタデータ世代を含め、食い違い時の扱いを定める。
厳密に揃える段階では本文応答に対応する作品情報を含める等、1回の応答で完結する方式を評価する。
単一スナップショット化だけでブラウザまでの原子的更新を保証したとは言わない。

## 5. 翌日分の先読み

### 判断

維持を推奨する。今日の閲覧が成功した後の翌日1作品だけで、利用に伴う小さな先読みだからである。
未利用の全作品を取得するバッチとは異なる。

- 今日の取得・表示を優先する。
- 翌日分が保存済みなら通常キャッシュを利用する。
- 失敗しても画面をエラーにせず、自動で繰り返さない。
- 初回取得の重複抑制は通常の本文取得と共用する。
- 全利用者が同じ「明日」を先読みするが、初回の分散重複は残る。

「人が開いた作品だけ」という厳密な意味ではないことを計画に明記する。
初期移行時や障害中に先読みを止められる小さな設定は有用だが、管理画面は不要。

## 6. 同時取得・保存障害時の負荷

### 判断

同一実行環境の取得共有と短い失敗後待機から始める。完全な取得回数保証はしない。
本文配信のために最初からDurable Objects等を追加する必要性は、現時点の測定では示されていない。

### 推奨仕様

- 進行中Mapのキーは作品IDとsourceRevision。共有結果はResponseストリームではなく本文等の再利用可能なデータ。
- 公式取得は1リクエストにつき1回。失敗直後の即時リトライはしない。
- 一時障害後は同じ実行環境で60秒程度の待機を初期提案値とする。429では有効なRetry-Afterを尊重する。
  待機情報には期限と件数上限を付け、Mapを無制限に成長させない。
- 待機中は、利用可能な正常キャッシュがあれば返し、なければ再試行可能なエラーとする。
- 保存処理の失敗が公式取得成功を取り消さない。ZIPのR2保存を優先し、KV保存は独立して試す。
  初期は書込み結果をawaitしてログを確実に取る。応答遅延が問題ならwaitUntil等へ移す。
- KVを分散ロック代わりに使わない。

KV/R2両方の保存が失敗しても、この取得共有だけでは後続の公式再取得を止められない。
成功本文を無期限にメモリ保持することは避け、保存失敗の継続を検知したら先読み停止などで負荷を抑える。
必要なら短時間・サイズ上限付きの本文保持や分散制御を別途追加する。

測定する指標: 作品ごとの公式取得回数、同時要求数、保存成功率、429/5xx、キャッシュ供給元。
観測値から重複率が問題と分かって初めて、分散抑制を追加する。

## 7. 実行上限とエラー分類

### 判断

ここは切り替え時にも確認する。キャッシュを使っても、初回にはZIP展開が必要になる。
通信待ち時間だけを見て「Workersの制限内」と判断しない。

Workersのメモリは128MB/isolateで、無料プランのCPU時間は10ms。
ネットワーク待ちはCPU時間に含まれないが、JSON解析・ZIP展開・文字コード変換は計測対象。
本番プランは未確認なので、無料枠で動くと確約しない。
[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

### 推奨検証

- 47927の短文と789の長編で、冷えた状態・KVヒット・R2ヒットを測定する。
- メタデータの約10.8MiBのJSON、展開済み文字列、応答JSONを同時保持する最大使用量を確認する。
- 異なる作品を同じ実行環境で並行処理する場合も確認する。
- ZIP受信サイズ・展開サイズ・同時処理数の制限を、測定とプランに基づいて決める。
- ZIPのContent-Lengthだけを信用せず、受信中・展開中の上限も実装可能か確認する。
- KVへ保存できないほど大きい本文は、R2を利用して提供できるなら本文全体を失敗させない。
- 10秒の取得タイムアウトに加え、ブラウザ→Next→Workers全体の待ち時間を揃える。
  現行ReadingClientの10秒タイマーは `/api/today` 向けで、本文取得には掛かっていない。

エラー分類の推奨:

| 原因 | 上流APIでの扱い |
| --- | --- |
| メタデータに作品なし・本文URLなし | 既存の404 |
| 著作権制限 | 既存の403 |
| 作品は存在するが公式ファイル取得に失敗 | 取得障害として503等へ整理。本文不存在の404と混同しない |
| 公式ZIP破損 | 取得データの異常として扱い、stageを記録 |
| キャッシュ保存のみ失敗 | 正常本文を200で返し、ログへ記録 |
| 想定外のコード例外 | 500と元例外ログ |

dayroaozoraの外部応答を今回は404/502の既存形式に保つことも可能。
ブラウザで旧版提供・利用停止を正しく区別する段階では、安定したエラーcodeを伝える追加変更が必要。
例外メッセージ文字列の解析で判別しない。

## 実装範囲への反映

1. まず公式本文・公式CSVへの切り替え、ログ、実データテスト。
2. キャッシュ読書きの耐障害性、実行環境内の取得共有、初回実行の上限確認。
3. 同一世代のメタデータ公開、版別本文キャッシュ、旧版提供の分類。
4. ブラウザ再検証・読書位置・CDNまで含む更新反映。

3と4を終えるまでは「訂正が画面まで反映される」と完了報告しない。
1と2で「公式取得への移行」を完了させることは可能。
全項目を必須にして緊急の切り替えを遅らせない。
ブラウザ更新・位置の移行を計画の最終段階に含める。従来の2〜4人日の見積もりは全体には適用せず、
応答契約と保存データ移行を具体化した時点で再見積もりする。
